Rewrite the comments in this file so they read clearly. Leave the code alone.

## What you are working on

A C++ port of a 1994 DOS puzzle game. The original is a Borland Pascal binary
and its source is lost, so the port was reconstructed by decompiling the
executable. The comments are where that reconstruction is recorded: they name
the machine address each rule came out of - `1000:86b8`, `DS:0x2056` - along
with measured counts, byte sizes, seeds and coordinates.

That makes these comments unusually load-bearing. A number in them is evidence,
not decoration. If a comment says a routine is called from three places, or
that a table measured 0.00%, or that a value is 0x18c, somebody read that out
of a disassembler and it is the only surviving record of it.

The prose around those facts, on the other hand, was written quickly and is
often overwritten. That prose is your job.

## Do not use a linter

There is a `prose-lint` skill and a `prose_lint.py` on this machine. Do not run
either, and do not run any other linter or scoring tool on this file. They are
part of a different step and will be run on your output afterwards.

A low score from that linter does not mean a file is finished. It counts
sentence length, hedging and filler, and it has no rule at all for the capitals
used as emphasis - which is the main thing you are here to fix. Files scoring
0.27 and 0.66 have been left untouched on the strength of a score while still
being full of shouting.

Read the file and judge it yourself.

## What to change

The comments shout. Words get capitalised for emphasis several times per file -
"it is BYTE-IDENTICAL", "written in ONE place", "the wave CLEARED" - and there
is some stray markdown bold. Converting those to ordinary prose is the single
most useful thing you can do, and you should do it in every file.

Beyond that, use your judgement on the writing: split what is tangled, cut
padding and hedging, straighten what is awkward, prefer active voice. You do
not need permission for a change that makes the meaning easier to see. Being
shorter is not the goal - being clearer is - so leave a long explanation alone
if it is already clear.

## What not to change

These are not style preferences. Each one has gone wrong on a real run.

- **Code, including its whitespace.** Not one character outside the comments. A
  previous run re-wrapped a C++ statement to fit the margin. If a code line is
  too long, leave it too long.
- **Indented blocks inside comments.** Anything indented four or more spaces is
  quoted Pascal, assembly, a register dump or a table lifted out of the
  original program. Reproduce it character for character, semicolons included.
  A previous run deleted the semicolons from quoted Pascal and left a record of
  the original's logic that no longer parses as Pascal.
- **Numbers.** Never paraphrase one. "Pages 1 and 3 measure 0.00%" must not
  become "match exactly" - that turns a measurement into an opinion about a
  measurement.
- **Certainty.** If the text hedges, keep it hedged. If it says three, do not
  write "several". Do not add confidence that was not there.

## Do not add anything

Do not write new comments. Do not annotate a constant that has no comment, and
do not restate a fact the surrounding text already gives - a previous run added
"// 26-column pane on the left" three lines below a sentence saying exactly
that. This is a cleanup: the file should come back with the same comments,
written better.

If something looks wrong or missing, leave it. Another editor reviews your
work afterwards and will handle it.

## House style

- ASCII only. Use `-`, not an em dash. A previous run replaced 16 hyphens with
  U+2014.
- Addresses, filenames and identifiers go `in backticks`. A previous run
  stripped all 102 of them out of one file.
- `//` comments, wrapped at 79 columns.
- Semicolons and dashes in prose are fine. Do not hunt them.
